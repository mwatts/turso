turso

Turso is a from-scratch Rust rewrite of SQLite. It offers three query frontends — SQLite/SQL, PostgreSQL, and an experimental Graph/Cypher dialect — and all three compile down to the same core/translate → core/vdbe → core/storage pipeline. The engine exposes two seams: the per-database Dialect trait and the per-connection FrontendCompiler registry. PostgreSQL and Graph/Cypher now both implement both seams — PostgresDialect+PostgresCompiler and GraphDialect+GraphCompiler — while SQLite implements only Dialect. The team keeps the frontends decoupled from each other at the crate level.

turso — Architecture Analysis

Executive Summary

Turso is a from-scratch Rust rewrite of SQLite. It exposes three independently-maintained query frontends that compile down to one shared relational engine. The native SQLite/SQL frontend uses sqlite/parser, which feeds core/translate. A PostgreSQL wire-protocol frontend wraps libpg_query in postgres/parser, and adds postgres/frontend, postgres/server, and the tursopg CLI. An experimental Graph/Cypher frontend, built from graph/cypher, graph/ir, graph/frontend, graph/runtime, and graph/temporal, compiles openCypher onto ordinary SQL tables plus label and relationship-type junction tables. All three frontends converge on core/translate → core/vdbe (execute.rs, an 18,212-line register-machine interpreter) → core/storage (btree.rs, wal.rs, pager.rs), with an optional core/mvcc row-versioning path.

Turso's main goal is SQL compatibility with SQLite, plus optional Postgres and Cypher dialects, on one storage engine. The project treats the engine, not the frontend, as the single source of correctness and durability.

Data Flows

  1. SQL path: the client sends text to SqliteDialect::parse, which calls turso_parser::parser::Parser and produces an ast::Cmd/Stmt. Connection::prepare passes this AST to core/translate, where plan.rs/planner.rs build a plan, optimizer::optimize_plan rewrites it, and emitter/ plus main_loop/ walk it to build a ProgramBuilder. Vdbe::step (execute.rs) then runs the program and drives BTreeCursor operations against btree.rs, wal.rs, and pager.rs. The engine returns each Row, or a final StepResult, to the caller.
  2. Postgres path: a wire-protocol client sends a query to TursoPgServer, which routes it through pgwire's simple- or extended-query handlers to PgConnection::prepare_statement. This method calls turso_pg_parser::parse and PostgreSQLTranslator::translate_with_prereqs, and produces the same ast::Stmt type that the SQL path uses. conn.prepare_translated_stmt then hands the statement to the same translate, VDBE, and storage pipeline described above. When pg_query rejects an engine-generated helper statement, PostgresDialect falls back to core::dialect::sqlite::parse.
  3. Cypher path: GraphConnection::query or execute calls turso_graph_cypher::parse, then Binder::bind resolves the result against a GraphCatalogSnapshot. The binder produces a bound PlanKind value, and lower_relational emits an ordinary ast::Stmt, built from SQL joins over the node and relationship tables and the label and relationship-type junction tables. This statement runs through the same translate, VDBE, and storage pipeline. A variable-length MATCH pattern instead routes through the __turso_graph_expand internal virtual table, which VDBE drives with ordinary best_index/VNext opcodes. This virtual table reads an in-memory CSR snapshot (TraversalSnapshot), rebuilt from committed and uncommitted B-tree rows. The database itself opens under GraphDialect, through turso_graph_frontend::open_database/open_database_with_io; GraphDialect delegates schema-row parsing to core::dialect::sqlite, registers a turso_graphs catalog vtab, and resolves the 24 temporal/cypher scalar names in turso_graph_temporal::FUNCTION_NAMES to turso_graph_temporal::dispatch, so those functions work with no separate extension install.
  4. Durability: by default, VDBE's commit-path opcodes append full changed pages to the WAL (storage/wal.rs), and the pager checks the WAL before it reads the main file. When a database sets PRAGMA journal_mode='mvcc', cursor operations instead route through core/mvcc's row-versioned MvStore, which writes a logical log of the affected rows only. Both paths share core/io's IOResult async abstraction, across the io_uring, IOCP, unix, and simulated backends.
  5. Replication: sync/engine reads committed WAL or logical-log state to replicate data to and from Turso Cloud. It works the same way regardless of which frontend produced the write.

Key Design Decisions & Patterns

  • One shared engine AST is the convergence point. All three frontends produce a turso_parser::ast::Cmd/Stmt value before they reach core/translate. Verified by: PostgresDialect::parse and lower_relational both return this exact type; neither feeds a frontend-specific IR into a second translator.
  • Postgres and Graph converge on using both engine seams. Dialect (core/dialect/mod.rs, added in commit 9b10c496d) is the per-database seam: identity, schema-row parsing, catalog registration, and function surface. FrontendCompiler (core/connection.rs:569, prepare_frontend at line 1115) is the per-connection seam: statement compilation, prerequisites, and reprepare. PostgresDialect+PostgresCompiler and GraphDialect+GraphCompiler (graph/frontend/src/dialect.rs, compiler.rs) both pair one of each. Verified by: GraphDialect::name() returns "graph-cypher" and implements turso_core::Dialect at dialect.rs:147, and GraphConnection::open_database pins it, byte-for-byte mirroring turso_pg::open_database. SqliteDialect implements only Dialect, because plain SQL compilation needs no separate per-connection seam. Graph schema still rides on SqliteDialect's catalog representation underneath — GraphDialect's schema-row methods delegate straight to core::dialect::sqlite, and it stores no marker prefix, unlike PostgresDialect.
  • The team decouples frontends from each other on purpose. Commit a7a22ff16 added a graph.cypher() adapter that coupled postgres/frontend to turso_graph_frontend, and commit 178437223 reverted it. Verified by: postgres/frontend/Cargo.toml and graph/frontend/Cargo.toml today list no dependency on each other, and both frontends compose only by calling Connection::register_frontend_compiler or opening a Dialect on the same shared core::Connection.
  • "Everything is a B-tree." FTS and vector indexes (core/index_method/backing_btree.rs), the graph frontend's label and relationship-type junction tables (graph/frontend/catalog.rs), and materialized-view bookkeeping (core/incremental) all persist through the one B-tree substrate. None of them invents its own file format. Verified by: all three route writes through the same core-storage-btree node in this graph.
  • A database chooses durability at runtime, not at compile time. PRAGMA journal_mode='mvcc' switches a per-database MvStore behind ArcSwapOption on Database. The default WAL path stays untouched when MVCC is off. This design keeps an experimental subsystem, marked not production-ready in docs/agent-guides/mvcc.md, opt-in per file.

Strengths

  • The frontends converge for real, not just in name. The Postgres and Cypher frontends produce the same AST type that the SQLite parser produces. The team writes and tests the roughly 89k-line core/translate optimizer and the 18k-line VDBE interpreter once, and all three dialects exercise them.
  • The two seams compose instead of forcing a single abstraction. A frontend that owns per-database schema state implements Dialect; a frontend that needs per-connection statement compilation, prerequisites, or reprepare implements FrontendCompiler. Postgres and Graph both need both and implement both; SQLite needs only Dialect and implements only that. No frontend forces the other into an ill-fitting single trait.
  • The codebase enforces storage-format reuse by construction. A new capability, such as FTS, a vector index, or a graph junction table, must express itself as B-tree tables; it may not invent its own on-disk format. This rule keeps the single-writer WAL, checkpoint, and backup story valid for every feature.
  • Conformance testing is extensive and kept separate per frontend. Each frontend has its own .sqltest-driven differential harness that checks it against a real reference: sqlite3 for SQLite, a spawned tursopg for Postgres, and the openCypher TCK plus CypherBench for Graph. Deterministic simulators and a B-tree content-hash tool (tools/dbhash) add storage-level checks.

Weaknesses & Risks

  • The Graph/Cypher frontend is unmerged and library-only. The repository's HEAD sits on feature/graph-frontend, and the graph-session node itself notes that no CLI subcommand and no language binding wires it in yet. Ten of this model's 46 nodes, and one full architectural layer, describe code that no user can reach from main or from any shipped binding today.
  • MVCC is not production-ready, but it sits on the hot commit path. docs/agent-guides/mvcc.md calls it explicitly not production-ready, yet core/vdbe wires straight into it (the core-vdbe → core-mvcc edge). A runtime PRAGMA turns it on, not a build flag, so an operator can switch a live database into this experimental path with one statement.
  • Several very large files sit at the center of the hot path. core/vdbe/execute.rs holds 18,212 lines, core/translate's optimizer holds 16,455 lines across 9 files, core/schema.rs holds 7,250 lines, and postgres/frontend/catalog.rs holds 4,093 lines. Every frontend's queries pass through these files, so their size raises review cost and concentrates risk.
  • The latest Cypher/TCK run shows a real failure rate. graph/test-results/REPORT.md, from run 20260721T115532, records 10,242 identities, with 8,800 passing and 1,442 failing. About 14% of the openCypher/CypherBench corpus does not pass yet.
  • An internal-helper bypass skips the database's own dialect. Engine-internal helpers always resolve functions with SqliteDialect semantics, no matter which dialect opened the database (StatementOrigin::InternalHelper). So a Postgres- or Cypher-opened database can still run SQLite-flavored internal SQL. Audit this seam if dialect-specific function semantics diverge further.

Recommendations

  1. Add a tags: ["unmerged"] marker to the Graph/Cypher frontend's nodes in this model. Do this so downstream readers of architecture_graph.json do not assume it ships on main.
  2. Write a compatibility matrix that lists which VDBE opcodes and dialects the team has validated against MVCC. Do this before you promote MVCC past experimental status. The core-vdbe → core-mvcc edge today implies all opcodes, which claims more than the work-in-progress status in core/mvcc's own docs supports.
  3. Split core/vdbe/execute.rs and the largest files in core/translate/optimizer along opcode-family or pass-family lines, where you can. Use the existing op_*-per-opcode structure as your guide; it makes a mechanical split lower-risk than it looks.
  4. Publish the CypherBench/TCK pass-rate trend, not just the latest run, alongside graph/test-results/REPORT.md. Triage the 1,442 failing identities into regressions and known gaps before you add any CLI or binding surface.
  5. Document the StatementOrigin::InternalHelper SqliteDialect bypass directly in core/dialect/mod.rs's own doc comment, not only in DESIGN_DECISIONS.md or the agent guides. Call out that it breaks the "one Dialect per Database" rule that the trait's public API otherwise implies.

Method & Limitations

This analysis combines directory traversal, direct reading of source files at the cited paths, tokei and wc -l line counts, and Cargo.toml dependency and workspace-member checks. It also checks git log and git branch against the specific commit hashes named in node descriptions (9b10c496d, a7a22ff16, 178437223); all three resolve in this worktree's history. It is not a compiler-derived call graph: edge types such as calls, depends, reads, writes, and emits come from reading code and commit messages, not from a symbol-level cross-reference tool.

The analysis covers the feature/graph-frontend branch: 52 Cargo workspace members, about 939 Rust source files, and about 557.8k lines of Rust, per tokei. The model covers a curated set of about 46 nodes, at crate and module granularity, to match the architecture-docs altitude guidance. Many individual optimizer passes, per-language binding internals, and single-purpose extension crates appear under one parent node instead of on their own.
